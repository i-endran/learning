Key Concepts

Java EE (now Jakarta EE) is a set of specifications that define a standard for developing enterprise Java applications. A Servlet Container like Apache Tomcat is a concrete implementation of some of those specifications, primarily the Servlet API. It manages the lifecycle of Servlets, handles network requests, and provides a runtime environment for your web application.

1. Client Request

Everything starts here. A user interacts with a browser, which constructs an HTTP request. This request includes the method (GET, POST), the target URL (`/users/123`), headers (like `Accept`, `User-Agent`), and an optional body (for POST requests).

2. Tomcat Connector

Tomcat's Connector component is a network listener. It's bound to a specific port (e.g., 8080 for HTTP, 8443 for HTTPS). It accepts the raw TCP connection from the client, parses the HTTP request, and creates `HttpServletRequest` and `HttpServletResponse` objects.

3. URL Mapping

The container inspects the request URL. First, it matches the hostname to a virtual Host. Then, it uses the path to find the correct web application (Context). Finally, it consults the application's deployment descriptor (`web.xml` or `@WebServlet` annotations) to find which Servlet is mapped to the request's URL pattern (e.g., `/users/*`).

4. Filter Chain (Request)

Before the request reaches the servlet, it must pass through a chain of Filters. Filters are used for cross-cutting concerns. Examples include a security filter that checks for a valid session, a logging filter that records request details, or a filter that decompresses incoming data. Each filter can inspect or modify the request before passing it to the next filter in the chain via `chain.doFilter()`.

5. Servlet `service()` Method

Once the request passes all filters, the container calls the `service()` method of the target Servlet instance. The default `HttpServlet.service()` implementation reads the request method (GET, POST, etc.) and calls the corresponding `doGet()`, `doPost()` method. This is where your core application logic resides.

6. Servlet Creates Response

Inside your `doGet()` or `doPost()` method, you process the request. This might involve querying a database, calling other services, and preparing data. Finally, you use the `HttpServletResponse` object to build the response. You set the status code (e.g., 200 OK), content type (`application/json`), headers, and write the response body (e.g., JSON or HTML).

7. Filter Chain (Response)

After the servlet finishes, the response travels back through the same filter chain, but in reverse order. This allows filters to process the outgoing response. A common use case is a compression filter that GZIPs the response body to reduce bandwidth.

8. Client Receives Response

Finally, the Tomcat Connector serializes the `HttpServletResponse` object back into an HTTP response and sends it over the network to the client. The browser then parses this response and renders the result to the user.

Core Components Deep Dive

Java web applications are built from a few key component types. This section provides code examples and explanations for the most important ones: Servlets and Filters. Understanding their lifecycle and purpose is fundamental to building robust backend services.

Servlets

A Servlet is a Java class that handles requests and generates responses. The container manages a single instance of each servlet and invokes it to handle multiple concurrent requests in separate threads. This makes thread safety a critical concern.

Servlet Lifecycle:

  • `init()`: Called once by the container when the servlet is first loaded. Used for one-time setup (e.g., loading configuration, initializing resources).
  • `service()`: Called for every incoming request. Dispatches to `doGet()`, `doPost()`, etc. This is where your logic lives.
  • `destroy()`: Called once when the container is shutting down or undeploying the app. Used to clean up resources.

Example:

public class UserServlet extends HttpServlet { @Override protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException { String userId = req.getParameter("id"); // In a real app, you'd fetch user data from a database String jsonResponse = "{\"userId\": \"" + userId + "\", \"name\": \"Jane Doe\"}"; resp.setContentType("application/json"); resp.setStatus(HttpServletResponse.SC_OK); resp.getWriter().write(jsonResponse); } }

Filters

A Filter is an object that can intercept and modify requests and responses. They are ideal for cross-cutting concerns like logging, authentication, authorization, and data compression. Filters are chained together, and each one decides whether to pass the request to the next filter in the chain.

Key Method:

  • `doFilter(request, response, chain)`: The core method. You place your pre-processing logic before `chain.doFilter()` and post-processing logic after it.

Example: Logging Filter

public class LoggingFilter implements Filter { @Override public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) throws IOException, ServletException { HttpServletRequest httpRequest = (HttpServletRequest) request; long startTime = System.currentTimeMillis(); System.out.println("Request Received: " + httpRequest.getMethod() + " " + httpRequest.getRequestURI()); // Pass request to the next filter or servlet chain.doFilter(request, response); long duration = System.currentTimeMillis() - startTime; System.out.println("Request Processed in " + duration + "ms"); } }

Resource Management

Efficiently managing resources like threads and database connections is crucial for building scalable, high-performance applications. Creating these resources is expensive. Resource pools solve this by creating a set of reusable objects, dramatically improving performance under load.

Thread Pools

Instead of creating a new OS thread for every single request (which is very slow), the application server (Tomcat) maintains a pool of worker threads. When a request arrives, it is assigned to an available thread from the pool. Once the request is complete, the thread is returned to the pool to be used for another request. This is a core feature you get for free with any servlet container.

Connection Pools

Establishing a database connection is a slow process involving network handshakes and authentication. A connection pool (using libraries like HikariCP or C3P0) pre-establishes a set of DB connections. Your application code "borrows" a connection from the pool, uses it, and then "returns" it. This is one of the most important performance optimizations in a database-driven application.

Security: SSL/TLS and Certificates

Securing web traffic with HTTPS is non-negotiable. This is achieved using the SSL/TLS protocol, which relies on digital certificates to establish trust and encrypt data. This section breaks down how the SSL/TLS handshake works to create a secure communication channel.

What are Certificates?

A digital certificate (like an SSL certificate) is a data file that binds a cryptographic key to an organization's details. It's issued by a trusted third party called a Certificate Authority (CA). When your browser connects to a website over HTTPS, the server presents this certificate. Your browser checks if it trusts the CA that issued the certificate. If it does, it can be sure it's talking to the legitimate server and not an imposter.

Simplified SSL/TLS Handshake

1. Client Hello: Client sends its SSL/TLS version and supported cipher suites.
2. Server Hello: Server picks a cipher suite, sends back its SSL Certificate (containing its public key).
3. Client Verification & Key Exchange: Client verifies the certificate. It then generates a symmetric session key, encrypts it with the server's public key, and sends it to the server.
4. Server Decryption: Server uses its private key to decrypt the session key.
5. Secure Communication: Both client and server now have the same symmetric session key. All further communication is encrypted using this key.
